# RFC-001: Kernel Change Process

## Tujuan
Dokumen ini mendikte aturan mutlak kapan dan bagaimana **AI Core Kernel** boleh diubah. Tidak boleh ada baris kode atau kontrak yang dimodifikasi tanpa mengindahkan protokol RFC (*Request for Comments*) ini.

## Kriteria Usulan (Kapan Boleh Mengubah)
Perubahan Kernel hanya diizinkan untuk:
- Memperbaiki kegagalan (*bug*) kritis / celah keamanan (Zero-Day).
- Menambah *Extension Point* baru untuk mewadahi kebutuhan Plugin generasi terbaru.
- Mengatasi disonansi performa yang tidak tertangani di lapisan SDK.

## Siapa yang Berhak Mengusulkan
Hanya arsitek sistem, tim *Core Infrastructure*, atau pengembang senior yang ditugaskan khusus yang dapat memicu pengajuan RFC. Pembuat Plugin tidak diperbolehkan mengubah kernel, melainkan harus mengirimkan *issue/RFC* terlebih dahulu.

## Tahapan Review & Approval Flow
1. **Drafting (Draft)**: Pengusul menulis RFC dengan rincian *Compatibility Impact* dan *Migration Strategy*.
2. **Architecture Review (Review)**: Dewan Arsitektur (termasuk CTO) membahas implikasi RFC terhadap skalabilitas, *security*, dan ketergantungan.
3. **Approval (Approved/Rejected)**: CTO menerbitkan *Executive Decision* (Go / No-Go).
4. **Implementation**: Setelah disetujui, perubahan diwujudkan.
5. **Certification Renewal**: Sertifikasi dan *Benchmark* (PERF, SEC, REP) harus disesuaikan kembali.

## Compatibility Impact & Semantic Versioning
Setiap modifikasi harus diklasifikasikan ke dalam:
- **PATCH**: Perbaikan *bug* tanpa ubahan kontrak. (Otomatis kompatibel).
- **MINOR**: Menambah API atau *Extension Point*. (Terkonfirmasi tak merusak plugin).
- **MAJOR**: Pembaruan struktural yang merusak (*Breaking Changes*). (Memerlukan Migrasi).

## Migration Strategy
Untuk level `MAJOR`, RFC wajib memuat dokumen teknis (panduan migrasi) agar tim Plugin (Company, Tender, dsb.) dapat menyesuaikan kode mereka ke format Kernel terbaru.
